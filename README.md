# 小说助手（wapp）

跑在自己电脑上的长篇小说写作管理器：管书籍与分卷、写章节正文、看写作节奏。

技术栈：**Electron + React + TypeScript + SQLite + Ant Design 6 + TipTap**。

选桌面端而不是 Web，理由只有一条但足够：**稿子是私产**。写到一半的正文不该为了
「有个编辑器」就上传到别人的服务器；本机 SQLite 直接读写，断网也能写。
「后端」即 Electron 主进程（Node.js）——前后端共用一门语言，不必为桌面壳
额外学一门语言（如 Tauri 需要的 Rust）。

## 快速开始

```bash
npm install              # 安装依赖
cp .env.example .env     # 可选：本地配置
npm run smoke            # 启动冒烟测试：验证整条链路是否真的通了
npm run dev              # 启动开发模式（热更新）
```

打包与图标：

```bash
npm run dist:win         # 产出 NSIS 安装包 + 免安装 exe（release/ 目录）
npm run dist:dir         # 只产出解包目录，便于快速验证
npm run icons            # 从 SVG 源重新生成 build/icons/ 与 build/icon.ico
```

其它脚本：

| 命令 | 作用 |
|---|---|
| `npm run typecheck` | 主进程 + 渲染进程全量类型检查 |
| `npm run build` | 类型检查 + 构建产物到 `out/` |
| `npm run smoke` | 自动化冒烟测试，全通过退出码 0 |
| `npm run preview` | 用构建产物启动应用（验证生产行为） |
| `npm run icons` | 重新生成应用图标（改图标设计后跑） |
| `npm run clean` | 清理 `out/` 与 `release/` |

> **关于原生模块**：`better-sqlite3` 从 v13 起发布的是 **Node-API 预编译产物**，
> ABI 跨 Node 与 Electron 版本稳定，**不需要**按 Electron 重新编译，也不需要
> 本机安装 C++ 工具链。这正是本项目选它的重要原因之一。
> 因此 `electron-builder.yml` 里显式设置了 `npmRebuild: false`。

> **关于网络**：项目根目录的 `.npmrc` 把 npm 源与 Electron 二进制下载指向了国内镜像。
> 如果你的网络访问官方源更快，直接删掉这个文件即可。

## 冒烟测试

桌面应用没有 HTTP 端点可以 curl，所以 `npm run smoke` 用一条等价路径替代验证。
它**用临时用户数据目录**启动真实主进程，绝不碰你真实的 `wapp.db`。

当前共 **78 项检查**，分三层：

**第一层 · 数据与接线**——数据库连接、迁移已应用、示例表已清理、41 个 IPC 通道注册齐备。

**第二层 · 业务规则**——这是主要部分，走的全是真实服务层调用：

- 计数口径：HTML 转文本的汉字统计、含标点字数、扩展区生僻字
- 书籍：新增 → **重名冲突拦截**
- 分卷：新增 → **跨书挂载拦截**（把 A 书的卷挂给 B 书必须被拒）
- 章节：新增 → 按需加载正文（列表不带 `content_html`）→ 元数据更新 →
  移入移出分卷 → **同容器内前移**（校验顺序与下标唯一性）→ 重排 →
  **不完整重排拦截**（只提交部分章节必须被拒）
- 大纲：自由嵌套 → **跨书挂载拦截** → **自身为父拦截** → **成环拦截** →
  **深度上限** → 子树级联删除 → 移动与重编号（同层下标不重复）→
  **落地成章节** → **重复落地拦截** → **章节占用去重** → 解除关联保内容
- 卡片库：专属字段写读一致 → **标签规范化**（去空白、去重）→ **同书同类型重名拦截** →
  **通用卡片重名拦截** → **跨书同名允许** → **类型切换时 extra 迁移**（旧类型的字段必须被丢弃）→
  **归属校验** → 三种书籍范围的筛选口径 → **类型计数忽略类型筛选** → **全文搜索命中正文** →
  **LIKE 通配符转义** → 复制（自动避开重名）→ 删除 → 删书级联
- 全库检索：切词与去重 → **多关键词 AND 语义**（两个词分属不同记录时必须为 0 处）→
  **同一记录内跨字段 AND**（标题一个词、正文一个词）→ 按来源分组（分组之和必须等于总数）→
  命中非默认字段（章节正文、书籍笔名）→ **LIKE 通配符转义** → 片段高亮区间自洽 →
  按书限定（通用卡片被挡在外面）→ 未知书籍返回 0 处而非报错 → 空查询不发 SQL →
  边界默认值与上限拦截 → 片段切片边界 → **检索只读**（跑完一圈计数必须分毫不差）
- 会话：**写作量 / 净增双口径**校验 → **异常会话拦截**（`peak < start` 会被边界校验拒绝）→
  **会话与正文自洽**（会话记录的字数必须等于正文实际汉字数——它是统计的唯一事实源，
  和正文对不上时首页那些「今天写了多少」全是错的）
- 统计：书籍聚合、趋势补零（区间内无记录的日子也要补 0）、热力图分级、总览、分书进度
- 删除：级联删除生效（章节、大纲节点、卡片）；**写作记录不随删书消失**
  （历史写作量是既成事实，不该被结构调整抹掉）

**第三层 · 渲染进程链路**——真的把窗口开起来，真的走进路由：

- 首页：React 挂载、健康检查 ok、指标区脱离 loading、渲染出真实书籍数与字数
- 大纲管理：树渲染出 4 行 / 4 个节点、已落地计数正确、**树面板实际高度**达标
- 卡片库：列表渲染 4 行 / 4 张、三类计数与通用计数正确、**编辑面板真的打开了一张卡**、
  **列表面板实际高度**达标
- 章节编辑器：进入 `#/books/:id/chapters/:id`，三栏齐备、正文字数与预期一致、
  目录有行、纠错报出问题、**墨色方向与纸面一致**、**底栏完整落在可视区内**
- 全库检索：顶栏输入 → 浮层出结果与来源分组 → **点开章节命中后跳到编辑器，
  且编辑器里选中的正是那个关键词** → **偏移人为跑偏（`at=99999`）时依然定位正确**

最后一项 **IPC 无静默失败** 是全局守门：整条渲染链路里任何一次 IPC 调用被拒绝都会让测试变红。

### 五条踩过坑的断言约定

1. **只认 `data-testid`，不认组件库的类名。**
   早期版本读的是 `.page__title` 这类自写样式类，换成组件库后类名全变，测试却「全部通过」
   ——因为 `querySelectorAll` 匹配不到时返回 0 而不是报错，成了假阳性。界面怎么改都不该
   影响断言，而元素真的丢了必须立刻失败，所以锚点一律自己挂。
2. **锚点要挂在自己写的元素上，不能挂在组件库的组件上。**
   `data-testid` 挂在 antd 的 `Tree` 上时，它不会把任意的 `data-*` 透传到 DOM——
   元素查不到，而树其实渲染得好好的（行数、高度全正常），断言只会报一句「树未渲染」。
   包一层自己的 `div` 最稳：既不依赖库的属性转发行为，也顺带给滚动区一个锚点。
3. **文案要验证方向，不只是存在性。**
   「墨色预设」的 `ink` 说的是**墨（字）**的颜色，CSS 却把 `--dark` 读成了「深色底」，
   给素白纸配了近乎白色的字——截图里只剩两条纠错波浪线浮着，字是隐形的，
   而所有断言全绿。现在纸面会在 DOM 上声明自己的墨色取向，测试比对**实测字色**与它是否自洽。
4. **布局缺陷要量几何，不能靠肉眼。**
   底栏被挤出窗口那次，DOM 查询一切正常、数字也对，只是 `bottom` 超出了窗口高度，
   而 `overflow: hidden` 又把它裁掉——**看不见也滚不到**。现在直接读 `getBoundingClientRect()`
   与 `window.innerHeight` 比；大纲页则量树面板的实际高度，高度链断掉时它会退化成内容高度，
   两栏的内部滚动随之静默失效。
5. **要读链路终点的值，不能读中间量。**
   从检索点进章节那一条，早期只断言「hash 变了、编辑器渲染出来了」——于是
   `extractDocText` 一个整体偏一位的坐标 bug 一路潜伏：`<p>abc</p>` 里 ProseMirror 的
   文档顶层内容从 0 开始、`a` 占 `[1, 2]`，而遍历是从 0 起步的，每个 span 都偏后一位，
   表现为「查找替换替掉的是旁边那个字」。现在断言读的是 `getSelection().toString()`
   ——用户真正看到的那个高亮。
   推论：**这条断言需要一个真能聚焦的窗口**。ProseMirror 只在自己拿到 DOM 焦点时
   才把选区写回 DOM，所以必须是显示了窗口的那几项才能读（见 `setWindowVisible`）。

## 架构约定

### 三层分层

```
IPC handler（控制器）  →  Service（业务）  →  Repository（数据）
   解析与校验              业务规则与事务        SQL 与行映射
```

- 控制器**不写业务逻辑**，也不吞异常。
- Service **不依赖 Electron / IPC 类型**，因此可以用真实数据库直接做集成测试，
  将来换传输层（HTTP、CLI）也不用改业务代码。
- Repository 是唯一写 SQL 的地方，避免 N+1。
- 校验统一收口在 `ipc-handler.ts` 的 `parse` 里，服务层不重复校验——
  但这也意味着**直接调服务层测不到校验**，所以冒烟测试里凡涉及「拦截」的用例
  都走真实的边界。

### 跨进程类型安全

`src/shared` 是唯一的契约来源。改一个字段，前端会直接编译失败，而不是运行时才报错。
表单的校验规则与主进程的边界校验用的是**同一份 Zod schema**，规则不可能漂移。

> **`null` 不是 `undefined`。** Zod 的 `.default()` 只对 `undefined` 生效，拦不住 `null`。
> 约定：渲染端用 `null` 表示「该筛选项不生效」，schema 就必须显式 `.nullable()`。
> 这条踩过坑——`books:list` 漏了 `.nullable()`，于是切换器的每次查询都被拒，
> 前端把失败降级成空下拉、页面照常渲染，缺陷只留在主进程日志里。

### 安全边界

| 措施 | 值 |
|---|---|
| `contextIsolation` | `true` |
| `nodeIntegration` | `false` |
| `sandbox` | `true` |
| 暴露给前端的 API | 仅 `preload` 中的显式白名单，无 `ipcRenderer` 本体 |
| 生产环境 CSP | `default-src 'self'`，仅构建产物注入（开发环境保留 HMR 能力） |
| 权限申请 | 一律拒绝，将来按 origin 白名单精确放行 |
| 外链 | 拦截站内跳转，交给系统浏览器打开 |
| 富文本粘贴 | `transformPastedHTML` 走白名单，`script` / `style` 直接剥除 |

### 错误处理与可观测性

- 每个 IPC 调用分配一个 **requestId**，同时出现在主进程日志和返回给前端的错误信封里。
  用户报错时凭这个 ID 可直接定位到那一次调用。
- 主进程**绝不返回堆栈**。前端只会看到规范化错误码 + 用户可读文案。
- 日志为结构化 JSON，写入 `%APPDATA%\wapp\logs\wapp.log`，超过阈值自动轮转为 `.1`；
  命中 `password / token / secret / cookie` 等 key 的字段自动替换为 `[redacted]`。
- IPC 边界统计**被拒绝的调用次数**，冒烟测试直接断言它为 0——
  这类错误最危险的形态是「前端降级后页面照常渲染」，靠人翻日志发现不了。

### 前端请求策略

- 4xx 类错误（校验、冲突、不存在）**不重试**；仅服务端内部错误自动重试，上限 3 次。
- 写操作**一律不自动重试**，避免重复写入。
- 删除走**乐观更新**：先摘掉该行，失败整体回滚，最后无论如何都 invalidate 保证最终一致。
- 加载态 / 空状态 / 错误态三态齐全，错误提示附带追踪 ID。
- React Query 的 `queryKeys.chapters` 刻意把 `lists` 与 `detail` 分开：
  自动保存只让列表失效、**不碰详情**，否则每次防抖落盘都会重取正文、
  把编辑光标顶回开头。

## 功能

### 书籍与分卷

书籍有状态（筹备 / 连载中 / 已完结 / 暂停）、封面色、目标字数、简介与标签。
详情页管分卷与章节：建卷、改名、拖拽排序、删卷（章节 `volumeId` 置空而不是级联删），
章节可在卷间移动、重排、删除。重排要求提交**完整**的章节顺序，只交一部分会被拒绝——
否则排序索引会出现空洞，下次重排结果不可预期。

### 大纲管理

一棵**自由多层情节树**。它与「卷 / 章」的物理结构**刻意分开**：大纲是写作前的构思，
卷章是成稿的容器，两者不是一回事——一条支线可能横跨三章，一个卷里也可能同时跑着
主线和两条支线。两种结构靠一个**可选**的关联打通。

- 节点类型：主线 / 支线 / 事件 / 伏笔 / 转折 / 备注；状态：构想 / 写作中 / 已完成 / 已废弃
- 任意嵌套（上限 12 层），拖拽调整层级与顺序，拖到某个节点上即成为它的子节点
- **落地成章节**：用节点标题新建一章并双向关联，树上显示章节名，点一下进编辑器
- **关联已有章节**：把节点挂到已有章节上，不改动章节内容
- 删除节点会级联删除子节点，删除前明确告知会影响多少个节点
- 记住上次在看哪本书（`localStorage`）

服务端有四条**硬约束**。它们不是顺手加的校验，而是这个数据结构的成立条件：

| 约束 | 不拦会怎样 |
|---|---|
| **成环** | 节点从任何根都走不到，在界面上凭空消失；递归渲染直接爆栈 |
| **深度上限** | 拖拽误操作能造出几百层，每层缩进把内容挤成一条竖线，拖拽下标换算的深度也随之失控 |
| **跨书挂载** | 把 A 书的节点挂进 B 书的树，B 书的树查询永远查不到它——数据还在，界面里没了 |
| **一个章节只被一个节点关联** | 「这一章要写什么」有两个答案，而作者往往意识不到自己挂重了 |

**环检测的做法**：从候选父节点**往上**走父指针，能走回自己就拒绝。
比「往下遍历自己的子树去找候选父节点」便宜得多——复杂度只跟深度有关，而深度有上限。

**移动的顺序由服务端算**：调用方只给「目标父节点 + 落点下标」，两个父节点下的新顺序
都由服务端基于数据库**当前**状态算出。客户端手里的树可能是旧的，并发拖拽时提交上来的
顺序会覆盖别人的改动。

**「源父节点要不要压缩」收在仓储层**：这个判断只有一处实现，调用方没有机会传错。
章节模块此前就先踩过一次——同容器内换位时多压缩了一遍源容器，把目标容器刚编好的下标
覆盖回去，出现重复的 `order_index`。表现是「把末位往前移会排错」，而且只有 2 个元素时
还会凭 id 大小**碰巧排对**，所以一直没被测出来。

**antd Tree 的拖拽落点有个坑**：组件对外暴露的 `dropPosition` 是「相对位置 **+** 该节点
在父节点中的下标」（即整棵树扁平化后的绝对行号），不是简单的 -1/0/1。直接拿它判断
前后会把节点插到错误的层级。落点下标还要在「去掉被拖拽节点之后」的兄弟列表里数，
与服务端口径保持一致，否则同层内往前拖会差一位。

**界面拦截只是即时反馈，真正的防线在服务层**：`allowDrop` 在拖拽过程中就挡掉非法落点，
让人不必拖完再看一个报错；但它是**体验**层的东西——键盘操作、将来的批量接口都可能绕过它。
服务层才是唯一能保证「不管从哪个入口进来都不会写坏数据」的地方，两边都要有。

### 卡片库

写作前的设定攒在这里，写的时候随手可查。三类卡片——**人物 / 物品 / 灵感**。

**三类共用一张表**（`cards`），靠 `card_type` 列区分，差异字段（人物有身份与关系、
物品有品阶与来源）放进 `extra` 这一列 JSON。选这个方案是因为它们的共性占了绝大部分，
于是三套增删改查只写一遍，将来加「地点」「势力」卡**不用改表结构、不用写迁移**。
（另一种做法是 `cards` 只留公共字段、另建三张扩展表，查询要 join，但每类能拿到真正的
主键约束与索引。当前三类都是「标题 + 简介 + 正文 + 标签」的同构形态，还不到那个必要。）

这个选择的代价是自己补上**数据库不会替你拦的东西**。四处关键的防线：

| 隐患 | 不拦会怎样 | 处置 |
|---|---|---|
| `extra` 是自由 JSON，字段名写错库不吭声 | 填了存不进去，或库里躺着永远不显示的幽灵字段 | `CARD_EXTRA_FIELDS` 一张表驱动三处：Zod 形状、表单渲染、类型切换迁移。写读两侧都过 `normalizeExtra` |
| 改类型时旧类型的字段会留下 | 人物卡改成物品卡后还带着「身份定位」，导出时才发现 | 同上。**这是统一建模最容易出错的地方**，`prepareWrite` 按目标类型投影 |
| 查通用卡片写成 `book_id = NULL` | `= NULL` 恒不成立 → 查重静默失效，建十张同名通用卡都不报错 | 一律 `IS`（NULL 安全比较）。冒烟里单独一条「通用卡片重名拦截」守着它 |
| 搜索关键词里的 `%` / `_` 没转义 | 搜 `100%` 变成「以 100 开头的一切」，看起来像「能搜到东西」 | `containsPattern` + `LIKE ... ESCAPE '\'`（`db/sql-utils.ts`，全项目共用一份） |

其余约定：

- **同书同类型下标题唯一**（不区分大小写）。范围收紧到「同书 + 同类型」是因为不同书里出现
  同名的「林澈」完全正常，人物卡与灵感卡同名也无所谓。这条挡的是「手滑又建了一张一样的卡」——
  两张看起来毫无区别的卡片，删的时候很难分辨该删哪张。
- **归属书籍可空**：`book_id IS NULL` 表示通用卡片（跨书通用的灵感常常如此）。
- **筛选范围三态**：全部书籍 / 指定某本书 / 仅通用卡片。后两者都不是 `bookId` 是数字还是
  null 能单独表达的，所以是一个显式的 `bookScope`。
- **类型计数忽略类型筛选**：选中「人物」时另外两类仍显示真实数量。把它们也筛成 0 的话，
  「物品 0 张」会让人以为物品卡没了，而不是「被筛掉了」—— 那是一组导航计数，不是结果集的分解。
- **列表连正文一起返回**，与 `chapters:list` 刻意不带正文相反。原因是量级差着几个数量级：
  一张卡正文上限 5000 字符、一页 60 张，最坏 300KB 的本地 IPC 载荷；换来的是点开一张卡
  不用再发一次请求，也不会在切换时闪一下空表单。
- **复制卡片**：人物卡常需要「同一个模板改几笔」。标题自动加「副本」后缀并避开重名
  （直接复用原标题会被唯一性规则拒掉，那样复制功能第一步就不可用），并且按标题长度截断，
  避免副本标题超限后「点保存就报错，而错因和标题长度看起来毫无关系」。

### 全库检索

顶栏一个搜索框（`Ctrl + K` 随时唤起），跨四张表一起搜：

| 来源 | 参与检索的字段 |
|---|---|
| 章节正文 | `content_text`（HTML 的纯文本投影）、标题 |
| 卡片库 | 正文、一句话简介、标签、标题 |
| 大纲 | 摘要、标题 |
| 书籍信息 | 简介、题材、笔名、书名 |

**用的是 `LIKE` 全表扫描，而不是 SQLite 的 FTS5。** 这个选择有实测依据：

| 方案 | 查询耗时（102 万字） | 索引体积 | 中文表现 |
|---|---|---|---|
| `LIKE` 全表扫描 | 6.0 – 6.7 ms | 无 | 子串匹配，完全正确 |
| FTS5 `trigram` | 0.03 – 0.10 ms | +7.75 MB | **查询少于 3 个字符直接返回 0 行，且不报错** |
| FTS5 按字拆 + phrase | 0.07 – 0.18 ms | +5.18 MB | 标点被分词器丢弃 → 搜「门外」误命中「舱门**，**外」 |

FTS5 默认的 `unicode61` 分词器把整句中文当成**一个 token**（`今天天气很好` 搜「天气」得 0 行、
搜整段得 1 行）。绕过它只有两条路，各有致命伤：`trigram` 要求查询至少 3 个字符，
而中文人名大多只有 2 字（「林澈」「星云」），搜出来是**静默的空列表**，用户会以为书里没写；
自己按字拆再拼 phrase 能支持任意长度，但标点会被分词器丢掉，相邻字符的判定与真实文本不符。

再看性能的真实量级：单本书 10 万字 **4.9 ms**，全库 1024 万字 / 2000 章 **52.5 ms**。
FTS5 快出的那 60 倍发生在 0.1 ms 与 5 ms 之间 —— 两者都在人眼感知阈值以下。
而代价是索引要多吃 5–8 MB、每次增删改都要维护索引、还要多一条迁移。
**用零索引、零维护、零误匹配换来用户感知不到的 50 毫秒，这笔交易是亏的。**

（顺带测过 `instr()`：比 `LIKE` 慢 64%，且对 ASCII 严格区分大小写，弃用。
`LIKE` 的 `%` / `_` 转义由 `containsPattern` + `LIKE ... ESCAPE '\'` 统一兜住。）

其余约定：

- **空格分词、全部命中（AND）**。搜「林澈 星云」找的是同时提到这两者的地方，
  而不是分别提到任一处的所有地方。多词之间是 AND，但**每个词可以在不同字段里命中** ——
  一个词落在标题、另一个落在正文，同样算这条记录满足全部词。
  没有引号语法、也没有排除号：一个小说写作工具不需要把自己的检索语法变成一门小语言。
- **切词与切片是共享层的纯函数**（`parseKeywords` / `sliceSnippet`），主进程与渲染进程共用一份。
  各写一份必然出现「界面显示搜了 3 个词、后端只搜了 2 个」，而这种不一致只在特定输入下才露出来。
- **片段锚点按「覆盖关键词种类最多」选**，不是简单取第一次命中。既然是 AND 检索，
  用户真正想知道的是「这几个词在哪儿同时出现了」；固定锚定第一次命中时片段里往往只有第一个词，
  用户看不到第二个词就在后面 40 个字处，会以为软件没看懂他的查询。
- **每来源一条 SQL**，靠窗口函数 `COUNT(*) OVER ()` 在一次扫描里同时拿到「命中总数」与「本页若干行」。
  拆成两条（一条 `COUNT`、一条取行）意味着正文要多扫一遍 —— 全库 1000 万字时那一遍是 50 毫秒，
  而窗口函数是免费的。它统计的是筛选后的全部行，不受 `LIMIT` 影响（窗口函数在逻辑执行顺序上更早）。
- **多取一条（`limit + 1`）判断截断**：比再跑一次计数便宜，且与 `LIMIT` 的口径天然一致。
- **空查询不发 SQL**。检索框刚被聚焦、还没输入是极高频的状态，让它扫一遍全部正文纯属浪费。
- **默认全库搜，不自动限定在当前这本书**。那种「聪明」会让「明明书里有、却搜不到」
  变成需要用户自己去猜的谜题；每条结果都标了所属书籍，全库搜的代价只是列表长一点。
- **结果只读，且不被任何写操作失效**。检索是瞬时的只读行为，浮层一关就没人看它了；
  挂进 `invalidateLibrary` 反而有害 —— 编辑器每 2 秒自动保存一次，每次都会让浮层在后台重跑全库扫描。
  时效性由 `staleTime: 0` 兜住（每次打开浮层都重新查一遍）。

**点开一条结果之后**：

| 来源 | 落点 |
|---|---|
| 章节 | `/books/:bookId/chapters/:chapterId?find=关键词&at=偏移`，编辑器滚动并选中命中的那一段 |
| 卡片 | `/cards?cardId=`，先复位筛选再选中那张卡 |
| 大纲 | `/outline?bookId=&nodeId=`，展开祖先链并选中该节点 |
| 书籍 | `/books/:id` |

章节的定位值得单说：**关键词负责「找得到」，偏移负责「是哪一次」**。

不能直接信任主进程给的偏移 —— 主进程搜的是库里的 `content_text`（由 `htmlToText` 产出），
编辑器手里是从 TipTap 文档算出的纯文本（由 `extractDocText` 产出），
两套投影的换行约定并不完全一致（列表这类嵌套块级结构会差上几个字符），
直接映射会把高亮标在错误的字上，而这类错误极其隐蔽，用户只会觉得「定位不准」。
也不能只用关键词 —— 一个词在一章里出现十次时，跳过去永远落在第一次，而用户点的是第五次。

所以编辑器用这个关键词在**自己的**文本里找出全部出现位置，再取离偏移最近的那一次。
偏移的漂移是「几个字符」级别，远小于同一关键词两次命中之间的间距，因此「最近」几乎总等于「原本那一次」。
冒烟测试里专门有一条断言用一个明显跑偏的偏移（`at=99999`）再走一次深链，
把这条设计锁住 —— 若有人图省事直接把偏移映射过去，那一次会落空。

### 章节编辑器（核心）

对齐成熟网文写作工具的三栏布局：

```
┌──────────── 顶栏：返回 · 查找 · 替换 · 取名 · 专注 · 发布草稿 ────────────┐
│ 题名 / 分卷 / 状态 / 目标字数（metabar）                                  │
├──────────┬────────────────────────────────────┬─────────────────┬──────┤
│ 章节目录 │  稿纸（工具栏 + 正文）              │ 纠错 / 废字 /   │ 校对 │
│ 分卷折叠 │                                    │ 预览（三选一）  │ 废字 │
│ 每章字数 │                                    │                 │ 预览 │
├──────────┴────────────────────────────────────┴─────────────────┴──────┤
│ + 新建章节 · 计划：剩 N · 纠错：N 处 · 本章：N（含标点 N） · 已保存     │
└────────────────────────────────────────────────────────────────────────┘
```

**纠错引擎**（`src/shared/proofread.ts`）是**纯函数**，不依赖 DOM，
因此主进程也能直接跑（冒烟测试就是这么用的）。五类规则：

| 分类 | 检查内容 |
|---|---|
| `punctuation` | 重复标点（`。。`、`，，`）、半角省略号、孤立的 `---`、**中英标点混用**（前一字符是汉字却用了半角标点） |
| `duplicate` | 助词/语气词连用（`的的`、`了了`、`地地`） |
| `mixedScript` | 中文里夹英文标点 |
| `pairing` | 引号与括号配对（含 `「」『』《》` 与嵌套） |
| `spacing` | 连续空格、汉字之间的多余空格、标点前空格 |

另有**废字检测**：按「冗余修饰 / 套话 / 宠物词」分组给出高频无信息量词表，
配合密度提示，帮作者发现自己的口头禅。

**正文高亮用 ProseMirror 装饰器（decoration）而不是 mark**：

> mark 会写进文档，`content_html` 里就会多出一堆 `<span class="proofread">`。
> 高亮是**阅读时的临时视图**，不是内容的一部分——一旦落盘，导出、统计、
> 将来换纠错规则时都得先清理旧标记。装饰器只活在视图层，文档保持干净。

**纯文本投影**（`doc-text.ts`）是编辑器与统计之间唯一的桥：
`extractDocText` 把 ProseMirror 文档转成带位置映射的纯文本，
`mapTextRange` / `positionOfOffset` 等做双向换算。纠错引擎吃纯文本、
产出的偏移再映射回文档位置去挂装饰；导出、字数统计、平台预览也都走这条投影。
好处是**纠错引擎可以完全不知道编辑器的存在**，可以单独测。

**自动保存**：防抖 2 秒落盘，`pendingRef` 里存的是 `{chapterId, html}` 配对。
只存 html 会出事——切章时旧章的正文可能被写进新章。卸载与路由切换时强制 flush。

**写作会话**（`use-writing-session`）：进入章节时以**已加载的汉字数**作为起点，
空闲 90 秒或不足 60 秒则不计入。起点不真实会凭空刷出几千字。

**平台预览**：按目标平台（番茄 / 起点 / 七猫 / 晋江 / 纸稿 / 纯文本）估算
每页字数、翻页数、阅读时长，用手机框呈现，点段落可跳回正文对应位置。
**明确标注是估算**——各平台规则会变，给不了像素级还原，但给得了「一段是不是太长了」这类判断。

**取名**：本地词库生成（风格 × 性别 × 字数），已取过的名字记在 `localStorage` 里避免重复。
不联网。

**查找替换**：基于纯文本 `indexOf` 定位，空替代替换用 `insertText` 而不是 HTML 解析。
「全部替换」按**从后往前**的顺序执行，避免前面的替换改变后面匹配的偏移。

**导出**：主进程 `dialog.showSaveDialog` 选择路径，支持 `txt` / `md`，
内容是 `content_text` 投影而不是 `content_html`——导出的是稿子，不是网页。

## 统计口径

三个数字容易混淆，这里定死：

| 名词 | 定义 | 用在哪 |
|---|---|---|
| **汉字数**（`hanziCount`） | 只算汉字，不含标点、数字、字母，**含扩展区生僻字** | 章节与全书字数、目标进度 |
| **含标点字符数**（`charCount`） | 非空白字符总数 | 与网文平台显示的字数对照 |
| **写作量**（`wordsWritten`） | 会话中**出现过的最高字数** − 起始字数 | 首页「今天写了多少」 |
| **净增**（`wordsNet`） | 结束字数 − 起始字数，**可能为负**（校对删字） | 书籍进度 |

写作量与净增是**两个不同的问题**：「今天付出了多少」和「稿子净涨了多少」。
用净增显示写作量会让勤快校对的作者得到负数，反过来用写作量算进度会虚高。
数据库只存 `start_words / end_words / peak_words` 三个原始值，两个派生字段在读取时算。

会话边界强制 `peak >= start`（schema 层）：`peak` 的初始值就是 `start`，
算出 `peak < start` 说明客户端采样逻辑有问题，这种数据写进去会污染**所有**派生指标。

连续天数按「今天没写但昨天写了仍算连续」处理。

## 界面与主题

### 为什么是 Ant Design 6

| 决策 | 理由 |
|---|---|
| 选 antd 而不是自研样式 | 表格排序、分页、表单校验时机、弹窗焦点管理、无障碍 aria 绑定——这些自研成本极高且容易做漏 |
| 选 **v6** 而不是 v5 | v5 配 React 19 需要额外打 `@ant-design/v5-patch-for-react-19` 补丁；v6 原生支持 React 19 |
| 不用 Tailwind 手写 | 数据密集型后台的核心是 Table 与 Form，这两块的复杂度恰恰是工具类 CSS 帮不上忙的部分 |

### 为什么编辑器是 TipTap（ProseMirror）

需要的是**结构化的文档模型**，不是富文本字符串：纠错要能拿「第 N 个字符」映射回文档位置，
导出要能投影成纯文本，将来大纲要能挂到段落上。contenteditable + innerHTML 做不到这些。
ProseMirror 的装饰器机制正好匹配「临时高亮」这个需求。

### 设计令牌（`src/renderer/src/theme/tokens.ts`）

组件能力用 antd，视觉规格按 Windows 11 调：

- **字体**：`Segoe UI Variable Text` → `Segoe UI` → `微软雅黑` 逐级回落
- **圆角** 8px、**控件高** 32px，对齐 Win11 控件规格
- **配色**取 Fluent Design 的强调色与语义色（`#0f6cbd`），而不是 antd 默认的蓝紫

浅色与深色**共用同一组尺寸令牌**，只切换颜色令牌与 antd 的颜色算法，
因此两套主题的间距、圆角、字号永远一致——这是手写 CSS 最难保持的部分。

### 深浅色主题

- 三态偏好：**跟随系统 / 浅色 / 深色**，默认跟随系统，写入 `localStorage`
- 颜色算法用 antd 的 `darkAlgorithm` / `defaultAlgorithm`，派生色阶自动与主色自洽
- 深色下主色按钮配**深色文字**：亮蓝底配白字对比度只有约 2.9:1，不达可读要求；
  换成深色文字后升到约 9:1，这也是 Fluent 官方深色主题的做法
- 主题同步到 `<html data-theme>`，供 `styles.css` 处理 antd 管不到的地方

### 编辑器外观与主题的关系

稿纸的**字体 / 字号 / 行距 / 背景 / 段落辅助线**是一套**独立于应用主题**的偏好
（写作者会挑顺眼的稿纸，不该被应用主题绑架）。实现上全部走 CSS 变量，
**不写进 `content_html`**——一旦外观变成内联样式，正文里就混进了呈现细节。

纸面预设自带 `ink` 字段，声明这层纸该配浅墨还是深墨。为避免「浅色纸配白字」这类
方向性错误，`ink` 会同时挂到 DOM 的 `data-paper-ink` 上供自动化测试核对。

### 新增前端模块的约定

1. 组件直接用 antd，不要再手写表格 / 弹窗 / 分页。
2. 需要被自动化测试断言的元素，挂 `data-testid`；需要暴露状态的，挂
   `data-state` / `data-loading` / `data-value` 这类 `data-*` 属性。
   **不要依赖 antd 的内部类名**（如 `.ant-table-row`）。
3. 颜色、间距不要写死，用 `theme.useToken()` 或设计令牌。
4. 通知统一走 `useToast()`，不要在业务代码里直接调 `message.xxx`——
   静态方法会脱离 `ConfigProvider` 上下文，深色主题下样式会不对。

## 数据

数据库文件位于 `%APPDATA%\wapp\wapp.db`（**不在安装目录**，避免权限问题，
且卸载时不会被删除）。

- `journal_mode = WAL`：读写并发不互相阻塞
- `foreign_keys = ON`：SQLite 默认关闭外键，已显式打开
- `busy_timeout = 5000`：遇到写锁等待而非立即失败
- `schema_migrations` 表记录已应用的迁移；每条迁移在独立事务中执行，失败整条回滚

表结构（迁移 `002_novel_schema`）：

| 表 | 说明 |
|---|---|
| `books` | 书名、状态、封面色、目标字数、简介、标签 |
| `volumes` | 所属书、卷名、排序索引 |
| `chapters` | 所属书 / 卷、题名、`content_html` + `content_text` + 两个计数字段、状态、目标字数 |
| `outline_nodes` | 大纲树节点（自引用 `parent_id`、可选 `chapter_id` 落地到章节），任意层级 |
| `cards` | 卡片库（人物 / 物品 / 灵感共用一张表，差异字段在 `extra` JSON；`book_id` 可空 = 通用卡片） |
| `writing_sessions` | 起始 / 结束 / 峰值字数、起止时间、时长 |

`content_html` 与 `content_text` 同时存是刻意的：前者是编辑器的真实文档，
后者是纠错、统计、导出的稳定来源。**列表查询不带正文**（只有详情带），
否则书架页会白拉几十万字。

`writing_sessions` 的外键是 `ON DELETE SET NULL`——删书不该抹掉「我当时写了多少」这个既成事实。

### 新增一次迁移

在 `src/main/db/migrations/index.ts` 的数组**末尾追加**：

```ts
{
  name: '005_add_chapter_notes',
  up(db) {
    db.exec(`ALTER TABLE chapters ADD COLUMN notes TEXT NOT NULL DEFAULT ''`)
  }
}
```

已发布的迁移条目禁止修改，否则老用户的数据库不会重新执行。

## 已知环境问题

### 启动即崩溃，日志里有 `GPU process isn't usable. Goodbye.`（退出码 3）

虚拟机、远程桌面会话、无独显的服务器上，Chromium 的 GPU 进程起不来并反复崩溃，
最终直接把应用带崩。解决办法是把 `WAPP_DISABLE_GPU` 设为 `true` 改用软件渲染：

```bash
WAPP_DISABLE_GPU=true
```

只调 `app.disableHardwareAcceleration()` **不够**，必须额外加 `--in-process-gpu`，
否则它仍会去创建 GPU 子进程。相关开关都必须在 `app.whenReady()` **之前**设置。

### `electron.exe --version` 打印出的是 Node 版本而不是 Electron 版本

说明环境里设了 `ELECTRON_RUN_AS_NODE`（某些 Electron 宿主程序会设置它）。
这会让 `electron.exe` 退化成普通 Node，应用无法创建窗口。运行时先清掉：

```bash
unset ELECTRON_RUN_AS_NODE
```

### 窗口高度算错的隐形陷阱：`antd` 的 `<App>` 会插一层 div

`App` 提供了一个 `div.ant-app`，它默认高度是 `auto`。如果祖先链上有
`height: 100%`，这一环会让它**无从解析**、退化成内容高度——于是整页比窗口高，
底部元素跑到窗口外，而 `overflow: hidden` 又把它裁掉，**看不见也滚不到**。

给这一层显式声明 `html, body, #root, .ant-app { height: 100% }` 才能接上高度链。
这类问题的典型症状是「DOM 查询全对、数字全对、就是看不见」，
所以冒烟测试直接量 `getBoundingClientRect().bottom`。

## 加新功能模块

以「时间线」（把卡片与大纲节点按故事内时间排成一条线）为例，需要新建表，6 步：

1. **`src/shared/modules/timeline.ts`** — 定义 DTO、常量与 Zod schema。
   这是**唯一契约来源**：主进程的边界校验与前端表单用的是同一份，规则不可能漂移。
2. **`src/main/db/migrations/index.ts`** — 在**数组末尾追加**一条迁移，已发布的禁改
   （改已发布的迁移，老用户的库不会重跑，只有新增迁移才能让「新装」与「升级」
   两条路径得到同一个 schema）。
3. **`src/main/modules/timeline/`** — 写 `repository`（唯一写 SQL 处）/
   `service`（业务规则与事务）/ `controller`（只解析 + 调用）三个文件。
4. **`src/main/ipc/registry.ts`** — 装配依赖并注册 handler；
   **`src/shared/api.ts`** 补 `WappApi` 类型；**`src/preload/index.ts`** 在白名单里加对应方法。
   漏一处前端就编译不过 —— 这正是跨进程类型安全的作用。
5. **`src/renderer/src/features/timeline/`** — 页面 + React Query hooks；
   `components/nav.tsx` 把 `ready` 改成 `true`（导航是唯一来源，首页入口卡片也读它），
   `App.tsx` 挂上路由，需要两栏各自滚动就往 `AppShell` 的 `FLUSH_ROUTES` 里加一条。
6. **`src/main/smoke-test.ts`** — 加业务规则用例与渲染检查。

前端照着 `src/renderer/src/features/cards/` 复制一份即可：筛选条 + 列表 + 编辑面板
的两栏布局，含分页、空状态、错误态与 `data-testid` 锚点。

> **建表时的一条约定**：只对**结构性不变式**加 `CHECK`（非空、非负、取值范围），
> 不对**枚举值域**加。SQLite 无法 `ALTER` 一个已有的 `CHECK`，改枚举值域必须走重建表；
> 而这些枚举（书本状态、卡片类型、大纲节点类型）恰恰是最容易随需求扩张的部分。
> 枚举值域由 `src/shared` 的 Zod schema 在 IPC 边界强制，两侧同一份定义。

> **「拦截」类用例必须走真实的 IPC 边界**：校验统一收口在 `ipc-handler` 的 `parse` 里，
> 服务层不重复做 —— 所以直接调服务层是测不到的（它永远不抛）。用
> `getChannelParser(IpcChannel.X)` 取真实校验器来跑，顺便也证明了控制器确实把 schema
> 挂上了，而不只是写在文件里。

> **顺手补一条断言：别让「新功能看起来是好的」骗过自己。** 卡片库这次的经验是，
> 凡是**新引入的建模方式**（三类共用一张表、字段塞进 JSON 列），都要专门为它
> 「数据库不会替你拦」的那一面写断言 —— 重名、幽灵字段、`IS NULL` 与 `= NULL`、
> LIKE 通配符。这些地方出问题时界面看起来完全正常。

## 启动失败怎么排查

1. 应用弹窗会直接给出原因（配置错误会列出具体哪一项非法）。
2. 看 `%APPDATA%\wapp\logs\wapp.log`，每行是一条 JSON，含 `level` / `msg` / `data`。
   搜 `IPC 调用被拒绝` 能看到所有被边界校验挡下的调用——包括前端静默降级掉的那些。
3. 主进程启动日志会打印 Electron / Node / Chrome 版本与数据库路径。
4. 前端右上角健康徽标悬停可看到版本、数据库大小、schema 版本与运行时长。
5. `npm run smoke` 能跑通说明链路本身没问题，问题多半在渲染层，用
   `WAPP_SMOKE_CAPTURE` 截图看实际长相。
